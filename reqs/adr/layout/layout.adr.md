# Repository layout decisions

## layout.adr-1 — Specs, rules and decisions live in `reqs/` at the repo root

- **status:** accepted
- **date:** 2026-09-14
- **context:** Verification material was split across three unrelated trees — `chrome-extension/tests/` for specs, `docs/decisions/` for decisions, `chrome-extension/requirements/` for business rules — with an `INDEX.md` placeholder in each of the latter two and nothing else. Nothing tied a spec to the source file it covered, `chrome-extension/tests/unit/` existed but was empty, and an e2e suite sat inside `tests/integration/` under an `.integration.` suffix. The solution-architecture skill requires one `reqs/` tree holding everything that verifies or justifies the app, mirroring the app path.
- **decision:** Consolidate into `reqs/` at the repo root: `integration/` and `unit/` mirroring `chrome-extension/`, a flat `e2e/`, `integration-examples/` mirroring the integration specs, `cross/` for cross-functional checks, `rules/` for static analysis, and `adr/<scope>/` for decisions. Vitest's root moves from `chrome-extension/` to the repo root so both trees are reachable from one root, and `vitest.config.js` moves with it. Alternative considered: keep `tests/` inside `chrome-extension/` and only rename — rejected, because specs are not packaged into the extension and nesting them under the packaged directory is what made the app path and the spec path diverge in the first place. Alternative considered: leave decisions in `docs/` — rejected, `ADR_LOCATION_CHECK` requires `reqs/adr`.
- **consequences:** Positive — a moved source file's spec is findable by path; coverage now measures `chrome-extension/**` rather than a hand-listed set of directories; one root for the whole verification tree. Negative — every spec's relative imports gained a `chrome-extension/` segment, and any in-flight branch touching `chrome-extension/tests/` will conflict. Risk — the extension still loads only what is under `chrome-extension/`, so anything the app imports must stay there. Mitigation — `constraints/` is placed under `chrome-extension/`, not at the repo root, and layout.adr-2 records why.
- **constraints:** none introduced
- **rules:** `reqs/rules/shared.boundary.js`, `reqs/rules/complexity.rules.js`, `reqs/rules/naming.rules.js` (moved out of the root `eslint.config.js`, which is now a loader only)
- **spec_changes:** architecture — all 15 integration specs re-pathed; the e2e suite moved to `reqs/e2e/workflows.e2e.test.js` and renamed off the `.integration.` suffix
- **specs_affected:** integration · e2e · cross
- **links:** downstream `layout.adr-2`, `shared.adr-1`

## layout.adr-2 — `constraints/` sits under `chrome-extension/`, not the repo root

- **status:** accepted
- **date:** 2026-09-14
- **context:** The skill's reference tree puts `constraints/` at the repo root "because the app imports from it as well as the specs, rules and ADR entries do". That reasoning assumes the app root and the repo root coincide. Here they do not: Chrome loads `chrome-extension/` as the unpacked extension, and a module outside that directory is not packaged, so `import '../../constraints/x.js'` from `chrome-extension/shared/` would resolve in Vitest and fail at runtime in the browser.
- **decision:** Place the constraints tree at `chrome-extension/constraints/`, keeping every other element of the reference layout. Specs import it across the boundary (`../../../chrome-extension/constraints/<owner>.constraints.js`), which is fine in the other direction — nothing in `reqs/` is packaged. Alternative considered: repo-root `constraints/` with a build step copying it into the extension — rejected, it introduces a generated file that can drift from its source and a build the project does not otherwise need. Alternative considered: duplicate the values in both places — rejected outright by `SINGLE_OWNER`.
- **consequences:** Positive — one declaration per boundary, importable by the app at runtime and by the specs at test time. Negative — the layout deviates from the skill's tree, so a reader following the skill literally will look in the wrong place. Risk — a future contributor "corrects" the path back to the repo root and silently breaks the packaged extension. Mitigation — this entry, and the header comment in each constraints file.
- **constraints:** introduces `template`, `workflow`, `agent`, `history`, `storage`, `version`, `shared`, `complexity` constraints files; `shared/constants.js` now re-exports them instead of declaring them
- **rules:** `reqs/rules/shared.boundary.js` and `reqs/rules/complexity.rules.js` both read their values from this tree
- **spec_changes:** implementation — four integration specs import their boundary values from `constraints/` instead of `shared/constants.js`
- **specs_affected:** integration · cross (`reqs/cross/version.spec.js`)
- **links:** upstream `layout.adr-1`

## layout.adr-3 — Shared doubles, harness and spec-driving scripts live in `reqs/support`

- **status:** accepted
- **date:** 2026-09-14
- **context:** `reqs/mocks/chrome-api.mock.js` and `reqs/setup.js` are neither specs nor examples: the first doubles an external dependency for eight suites across two levels, the second installs that double, resets storage between cases, and registers custom matchers. Filed as they were, `reqs/mocks/` named a role rather than a subject, and `reqs/setup.js` sat loose at the root of a tree where every other file states a requirement. Neither asserts anything, so counting them alongside specs blurs what the suite actually covers.
- **decision:** Collect under `reqs/support` every method, script, command, harness or double that serves the specs rather than stating a requirement — including anything resolving cross-module relations or an external dependency for more than one level. Files are named for what they double or drive (`chrome-api.mock.js`, `vitest.setup.js`), never for their role. Alternative considered: keep `reqs/mocks/` and add sibling role-named directories (`reqs/helpers/`, `reqs/harness/`) — rejected, each new kind of scaffolding would invent another top-level directory and none is named by subject. Alternative considered: colocate every double beside its first consumer — rejected for a double eight suites share, though it remains right for a single-consumer stub.
- **consequences:** Positive — one place to look for scaffolding, named by subject, and a directory the gate can exclude from coverage without listing files. Negative — a single-consumer double now has two plausible homes, so the "second consumer" rule has to be applied by judgement. Risk — `reqs/support` becomes the junk drawer `reqs/mocks` was starting to be. Mitigation — SUPPORT_ON_DEMAND in the skill: a file arrives there when a second consumer needs it, not before.
- **constraints:** none introduced
- **rules:** none changed
- **spec_changes:** architecture — ten suites re-point their mock import to `reqs/support/`; the runner's `setupFiles` points at `reqs/support/vitest.setup.js`
- **specs_affected:** integration · e2e
- **links:** upstream `layout.adr-1`

## layout.adr-4 — Specs are filed by how many real modules they exercise, not by folder habit

- **status:** accepted
- **date:** 2026-09-14
- **context:** Every spec in the project lived under `reqs/integration`, but twelve of the fourteen doubled the app modules their subject collaborates with (`vi.mock('.../storage.js')` and similar), leaving exactly one real module per suite — the definition of a unit spec. `reqs/unit` was empty. The remaining two, for `background.js` and `sidepanel.js`, imported no app module at all: each built a stand-in DOM, re-implemented the behaviour inline and asserted against its own copy, so both modules reported 0% coverage across roughly a thousand passing lines. The level a spec is filed at is what tells a reader whether a failure indicts one module or the contract between several; filed uniformly, it told them nothing.
- **decision:** File a spec by what it actually exercises. A suite with one real app module and doubled collaborators is a unit spec under `reqs/unit/<app-path>`, named `<module>.test.js`; a suite keeping two or more app modules real and doubling only the platform edge is an integration spec under `reqs/integration/<primary-module-app-path>`; a suite with no primary module is an e2e flow. The twelve move to `reqs/unit` and `reqs/integration-examples` follows them to `reqs/unit-examples`. The two suites that asserted against their own re-implementations are rewritten to import the real module — `background.js` boots on import and is driven through the listeners it registers; `sidepanel.js` boots on DOMContentLoaded against the project's real `sidepanel.html`, not a hand-written stand-in, so a renamed container fails the spec instead of passing against stale markup. Alternative considered: keep the twelve where they are and call the distinction cosmetic — rejected, the level is the only signal of blast radius, and an empty `reqs/unit` beside a full `reqs/integration` misreports what the suite covers. Alternative considered: delete the two tautological suites rather than rewrite them — rejected, both modules are load-bearing and reachable; the coverage they were pretending to give is coverage the project actually needs.
- **consequences:** Positive — 242 cases now all assert against real modules; `background.js` goes 0% → 44% and `sidepanel.js` 0% → 35%, lifting the project from 41.8% to 50.4% statements, so the floor rises from 40 to 45. The sidepanel suite loads the shipped markup, so the page and its module can no longer drift apart silently. Negative — the case count falls from 258 to 242, because roughly a thousand lines of self-referential assertions were replaced by twenty-two real ones. Risk — booting a module by importing it for its side effects is timing-sensitive, and both suites wait on an observable rather than an awaited promise. Mitigation — each wait is on a specific post-init observable, and each new case was verified to fail against a deliberately introduced regression (a renamed container id, removed output escaping, a changed menu cap) before being trusted.
- **constraints:** none introduced
- **rules:** none changed; the coverage floor in `vitest.config.js` rises from 40 to 45
- **spec_changes:** architecture — twelve specs move to `reqs/unit`, examples to `reqs/unit-examples`; implementation — the background and sidepanel suites are rewritten against their real subjects
- **specs_affected:** unit · integration
- **links:** upstream `layout.adr-1`, `layout.adr-3`

## layout.adr-5 — A browser smoke level under `reqs/browser/`, run outside Vitest

- **status:** accepted
- **date:** 2026-09-14
- **context:** Every level under `reqs/` runs in jsdom with `chrome.*` doubled, so no spec in the project can fail for the reasons an extension actually breaks on a user's machine: Chrome refusing `manifest.json`, a page script whose module specifier resolves under Vitest's bundler-shaped resolution but 404s against Chrome's loader (the `EXPLICIT_JS_EXTENSION` failure mode, which is invisible to ESLint _and_ to the suite), a service worker that never registers, or a panel that boots with a console error. Renaming `sidepanel.html`'s `<script src>` to a file that does not exist leaves all 363 jsdom cases green.
- **decision:** Add one level above e2e: `reqs/browser/<flow>.smoke.js`, flat and named for the flow, driving a real Chrome with the unpacked extension installed through the `chrome-devtools` CLI, and run by Node's own test runner (`npm run test:smoke`, `node --test --test-concurrency=1`) rather than by Vitest, which has no browser here. The CLI is driven from one support file, `reqs/support/chrome-cli.driver.js`, introducing a third support role, `<runner>.driver.js`, beside `.mock.js` and `.setup.js`; like them it states no requirement. The level is deliberately thin — boot, seed, one template run, persistence across a reopen — because everything that can be localised belongs at a cheaper level (`E2E_FEW_AND_LOAD_BEARING` applies here with more force). Alternative considered: add the browser cases to `reqs/e2e/` — rejected, `vitest.config.js` collects that directory and the cases cannot run under Vitest; a suffix inside a collected directory that the runner cannot execute is worse than a directory it does not collect. Alternative considered: a headless browser runner (Playwright, WebdriverIO) as a dev dependency — rejected for now, the project already depends on `chrome-devtools-mcp` and its CLI, and one more runner buys nothing the CLI cannot do here. Alternative considered: leave this uncovered and rely on manual loading — rejected, that is exactly how `sidepanel.js` and `background.js` reached 0% coverage while looking tested (layout.adr-4).
- **consequences:** Positive — the failure classes above now fail a check: the deliberate `<script src>` break turned four smoke cases red while `npm test` stayed green, which is the evidence this level exists for. The run is ~17s and needs no API key, because it drives the demo provider. Negative — it needs a real browser and the `chrome-devtools` CLI on the machine, so it is neither part of `npm test` nor of CI, and a check outside CI is a check that can rot (`RULES_RUN_IN_CI` is knowingly not met here). The demo provider fails one call in ten by design, so the run case retries rather than asserting a single attempt. Risk — the level grows into a second e2e suite, slow and flaky, and drags the feedback loop with it. Mitigation — the suite is capped at load-bearing flows by the same rule that caps `reqs/e2e/`, and each case must state what it can catch that jsdom cannot.
- **constraints:** none introduced
- **rules:** `.claude/rules/browser-specs.md` added; the role table in `.claude/rules/specs.md` gains `<flow>.smoke.js` and `<runner>.driver.js`
- **spec_changes:** architecture — a fifth level, `reqs/browser/`, with its own runner and npm script (`test:smoke`)
- **specs_affected:** browser (new) · none of the existing levels change
- **links:** upstream `layout.adr-1`, `layout.adr-3`, `layout.adr-4`

## layout.adr-6 — The coverage floor rises to 65 as the two uncovered modules gain specs

- **status:** accepted
- **date:** 2026-09-14
- **context:** `settings.js` (495 lines) and `content.js` (419 lines) were the two modules the skill's `COVERAGE_GAPS` rule named: reachable, load-bearing, and at 0% with no spec, which is why the floor sat at 45 while the rest of the project measured far higher. Six new suites — the settings page, the content script, and the contracts between workflow-manager, template-manager, history-manager, agent-runtime and the editor tab — take the project from 50.4% to 67.7% statements. A floor left at 45 would let all of that regress silently.
- **decision:** Raise `vitest.config.js` thresholds to 65 statements / 65 lines / 65 functions / 60 branches — under the measured 67.7/67.7/69.6/62.3, so ordinary churn does not fail the build, but close enough that losing a suite does. Alternative considered: set the floor at the measured number — rejected, a floor equal to the current value turns every unrelated refactor into a coverage failure. Alternative considered: leave it at 45 — rejected, it no longer describes anything true about the suite, and `COVERAGE_GAPS` exists because an unmeasured module is how both page modules reached 0% unnoticed.
- **consequences:** Positive — `settings.js` goes 0% → 72.8% and `content.js` 0% → 70%; `agent-runtime.js` reaches 100% statements; the gap the skill named is closed and the floor now guards it. Negative — a contributor deleting or skipping a suite now fails `test:coverage` rather than merely lowering a number. Risk — the floor becomes a target and specs get written for coverage rather than for behaviour. Mitigation — `SPEC_ASSERTS` and `PROVE_IT_FAILS`: each of the new cases was verified red against a deliberate break of the thing it covers before being trusted.
- **constraints:** none introduced
- **rules:** the coverage thresholds in `vitest.config.js` rise from 45 to 65 (branches 60)
- **spec_changes:** implementation — six new suites under `reqs/integration/` and `reqs/unit/content/`
- **specs_affected:** unit · integration
- **links:** upstream `layout.adr-4`

## layout.adr-7 — One `.spec.js` suffix, and case titles that name their subject in Gherkin

- **status:** accepted
- **date:** 2026-09-15
- **context:** Two conventions were doing one job. The suffix split the tree — `.test.js` at three levels and `.spec.js` at the fourth — so "is this file collected?" and "which level is it?" were two different questions answered from two different places. Titles were worse: 345 cases carried free prose (`should handle malformed API responses`, `Boot`, `Scenario: Basic storage operations`), with no subject in the line and no marker of whether a `describe` stated a precondition or an action. A failing line in a 363-case run named a rule but not its owner, `grep` over the run output answered nothing about coverage, and nothing mechanical held any of it — the convention lived in whatever the last reviewer remembered. The constraints → examples → specs chain was already in place; what was missing was the part of it a reader actually sees.
- **decision:** Every collected spec ends `.spec.js`, with the level stated as an infix before it: bare for unit, `.integration.`, `.e2e.`, `.cross.`. Every block title reads `Subject[.Component]: <keyword> <clause>`, the keyword fixed by depth — outer `describe` is `Given` the preconditions, a nested `describe` is `When` the condition, `it` is `Then` the expected result — and the first dotted segment must match the spec file's own base name. `reqs/rules/spec-titles.rules.js` enforces the pattern, the subject, and per-file title uniqueness, deriving the expected subject from the file path rather than from a catalogue of module names, which `SELF_DESCRIBING` forbids. Alternative considered: keep `.test.js` and add the titles alone — rejected, the suffix split was the other half of the same question and both cost one rename. Alternative considered: validate titles against a hand-maintained `modules.json`, as the project this convention is drawn from does — rejected, that is an index file the tree already encodes, and it falls behind the first time a module is renamed. Alternative considered: state the convention in `.claude/rules/` and leave it to review — rejected by `APPROACH_IS_EXECUTABLE`; the previous prose convention is exactly what produced 345 titles in four different styles.
- **consequences:** Positive — the run output is now the coverage report: `--reporter=verbose | grep TemplateManager` lists what that module is held to, a failure names its owner, and the suite reads top to bottom as a specification. The title contract is a lint error rather than a review note. Negative — 23 files were renamed and 345 titles rewritten in one change, so `git log --follow` and any open branch touching a spec pay for it once. The mechanical rewrite left some `Then it …` clauses stiffer than a hand-written one would be. Risk — the subject prefix repeats on every line and reads as noise, tempting someone to drop it. Mitigation — the prefix is what makes the output greppable by module; that is the whole return, and the lint rule keeps it from eroding quietly.
- **constraints:** none introduced; the title patterns live in `reqs/rules/spec-titles.rules.js`, not in `chrome-extension/constraints/`, because nothing the extension ships has to agree with them (`NOT_EVERY_LITERAL`)
- **rules:** adds `reqs/rules/spec-titles.rules.js` (`gherkin-title`, `title-subject`, `no-duplicate-title`), loaded by `eslint.config.js`; each was observed failing against a deliberate violation before being trusted
- **spec_changes:** architecture — every spec file renamed to `.spec.js` with a level infix, `vitest.config.js` include globs rewritten to match; implementation — 345 case titles rewritten to `Subject: Given/When/Then …`
- **specs_affected:** unit · integration · e2e · cross
- **links:** upstream `layout.adr-1`, `layout.adr-4`
